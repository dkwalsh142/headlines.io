# Headlines.io — Project State (2026-09-29)

A Timeguessr/Wordle-style game: each round shows 5 real historical NYT headlines,
one at a time, and the player guesses the publication year. This doc is a
snapshot for picking up a conversation about **furthering the UI** — animation,
sound, and general visual design — in a fresh session that has no prior context
on this project. Everything below is either directly relevant to that
discussion or necessary background to understand the constraints it sits in.

## Where things stand, in one paragraph

There's a working content pipeline (fetch NYT headlines → LLM pre-score →
manual curate/approve → group into pools → schedule pools to dates → build
rounds.json), a local browser tool for doing all of that curation/scheduling
by hand, and a playable React game with a full round loop and a first-pass
**pixel-art newspaper** visual theme. Nothing is deployed publicly. The stats
backend (same-day "vs other players" comparison) is designed but not built.
Right now there are 10 real playable rounds built from hand-curated headlines.

## Content pipeline — how headlines become rounds

Two decoupled phases, by design (a curator's judgment call on *what 5
headlines go together* is separate from *what date they run on*, and each
needs to be independently revisable):

1. **Pool creation** — group exactly 5 approved headlines into a `pool-NNNN`
   entry. No date attached. Array order = play order (no separate position
   field). Enforced in both the CLI and the browser UI: **exactly 5, always**
   (hard block, not a warning — this was tightened from the original design
   doc's "warn, never block" stance specifically for headline count).
2. **Day assignment** — assign a pool to a `YYYY-MM-DD` date in
   `schedule.json`. Reassignable/unassignable freely up until it ships.
3. **Build** (`build-rounds.js`) — joins pool + schedule into `rounds.json`.
   Re-runnable any time, **except** it never touches a date that's already
   "shipped" (date ≤ today AND already has an entry in rounds.json from a
   prior build) — those are frozen byte-for-byte even if the schedule or a
   headline's difficulty rating later changes underneath them.

The browser curation UI (`localhost:5177`) has two tabs: **Curate** (review
raw NYT headlines one at a time, approve with difficulty 1-5 + a section tag,
or reject) and **Schedule** (browse/search all 416 approved headlines with
filters — text search, section, year range, hide-already-scheduled,
hide-already-in-a-pool — select exactly 5 into a pool with live warnings for
same-decade/same-section clashes, reorder or swap headlines within an
existing pool, assign pools to dates, build rounds.json). Inline editing of
headline text (typo fixes) is also there, since text only lives in one place
(`approved.json`, referenced everywhere else by id).

Fixed section vocabulary: `politics, world, business, sports, arts, science,
opinion, style`. Fixed day boundary: midnight UTC everywhere.

**Current data state:** 416 approved headlines, 10 pools built into 10
consecutive scheduled rounds (2026-09-28 through 2026-10-07), spanning
headline years 1901-2026 across all 6 sections currently in use (world,
sports, business, arts, politics, science — opinion/style exist in the
schema but aren't populated yet). Raw fetch coverage is partial (months
March/June/July fetched for varying year ranges out of 1900-2026); ~57% of
fetched articles have gone through LLM pre-scoring so far.

## The game itself — what's built

**Game loop** (`RoundPlayer.jsx`): `showing_headline → awaiting_guess →
revealing → next_headline | round_complete`, exactly per the design doc.
Player sees a headline + its section tag, taps "Guess the year", types a
year, sees the reveal (their guess vs. actual + points), then either the next
headline or the round-complete screen (total score + full per-headline
breakdown, including a link to the real NYT archive article for each one).

**Scoring** (`scoring.js`): exponential decay, `1000 * 0.5^(distance/10)`,
so a guess within 10 years still scores ~500, tuned to the backlog's roughly
125-year span. Rounded to the nearest integer.

**"Today's round" vs. beta mode**: the shipped-game model is one round per
day, looked up by date. Since there's no live stats backend yet and testing
needs to actually play things, `App.jsx` also has a "Beta access — all
rounds" section listing every round in rounds.json, playable in any order —
explicitly labeled as dev-only scaffolding that won't exist in the shipped
game.

**Not built yet:**
- The stats service (§7 of the design doc) — same-day "you beat 72% of
  today's players" comparison. The round-complete screen currently only
  shows the player's own score, no comparison.
- Player identity (`localStorage` UUID, per the design doc) — not needed
  yet since there's no backend to submit to.
- The September 11 memorial-page special case from the design doc (explicit
  content requirement, deferred — not yet enforced in the scheduling tools
  either, noted as a known gap).
- Any deployment/hosting — everything is local dev servers only.

## Current visual design — the pixel-art newspaper theme

This is the part most relevant to furthering the UI, so more detail here.

**Concept**: a "pulp-era newspaper" look rendered in pixel art — aged paper
background, black ink text, a red accent used like a rubber stamp (section
tags, primary buttons, score highlights). Deliberately no dark-mode palette
swap — treated as a fixed print aesthetic rather than a theme-aware UI.

**Typography** (two-tier, both bitmap/pixel fonts, no smooth sans-serif
anywhere in-game):
- **VT323** (Google Fonts, free) — a pixel terminal/teletype font, used for
  all smaller UI chrome: buttons, scores, section badges, the "headline N of
  5" counter, the results-list recap text, form inputs.
- **Alagard** (`public/fonts/alagard.ttf`, downloaded — license was stated
  as confirmed by the user but not independently verified) — a chunkier
  pixel/blackletter display font, used only for the two most prominent
  headline moments: the "HEADLINES" masthead on the home screen, and the
  actual historical headline text shown during play. Reserved for large
  text since it's less legible at small sizes than VT323.

**Chrome/borders**: no `border-radius` anywhere. A reusable `.pixel-frame`
CSS class draws a stepped, hard-cornered border via four stacked
`box-shadow` offsets (not an image asset) — applied to every card, list
item, and form input. This was a deliberate choice over an uploaded
pixel-art frame image, reasoned through explicitly: headline text is
variable-length (one line to three), so a raster frame image baked to a
fixed size can't reflow around it — CSS-drawn chrome scales with content,
real image assets are reserved for things that don't need to flex around
text (icons, textures, ornaments — none built yet).

**What's completely static right now**: there is no animation or motion
anywhere in the app — no transitions between game-loop phases, no reveal
animation, no button press feedback beyond a 2px CSS `translate` on
`:active`, no loading states beyond a plain "Loading…" text string. There is
no sound at all — no music, no SFX for guess submission, reveal, correct/
close/far feedback, or round completion. Section badges are text-only
(single/double-letter abbreviations were considered for one context but
never became icons). No pixel-art iconography, no decorative texture/noise
beyond a very faint 3px repeating-gradient scanline on the body background.

## Things worth bringing into a UI/animation/sound discussion

- The **game loop's phase transitions** (`showing_headline → awaiting_guess
  → revealing → next_headline`) are the natural hook points for animation —
  right now they're instant React re-renders with zero transition.
- The **reveal moment** (guess vs. actual, point award) is the emotional
  peak of each headline and currently has zero motion or sound — probably
  the highest-value place to start.
- The **round-complete screen** (total score reveal + per-headline
  breakdown list) is the other obvious animation/sound moment — a "big
  reveal" now just appears fully-formed.
- Scoring is continuous (exponential decay), not tiered/bucketed — so any
  "near miss" vs "way off" feedback (sound, color, animation intensity)
  would need to derive its own thresholds from the score or raw year
  distance, since none currently exist in the data model.
- Section is a fixed 8-value enum already flowing through every headline
  record — a natural axis for per-section theming (icon, accent color,
  sound sting) if that's wanted, mentioned in the original design doc as
  "essentially free once section is a first-class field."
- The pixel-frame/font system is component-agnostic CSS, not baked into
  specific markup — new components can reuse `.pixel-frame` and the two
  font variables (`--pixel-font`, `--headline-font`) directly.
- No animation or audio libraries are installed yet — this is a fully open
  choice (CSS transitions/keyframes vs. something like Framer Motion; Web
  Audio API vs. Howler.js vs. plain `<audio>` tags, etc.).
- Everything is local-only static JSON with no backend — any UI decision
  that implies server state (e.g. streaks, live leaderboards during a
  round) would need the deferred stats service first.
